# 图像压缩

**id** `compress_image` · **分类** 图像

把图像编码得更小。两条完全分开的路：

- **无损** —— 走 [`png_opt`](../png-optimization.md)：颜色类型、位深、调色板、逐行滤波、
  压缩级别、元数据全都过一遍，只留最小的那一份。像素一个都不改。
- **有损** —— 要么转 JPEG（照片），要么量化成调色板 PNG（像素画）。量化是**有损**的，
  和无损那条路毫无交集。

## 端口

| 方向 | 端口 | 类型 |
| --- | --- | --- |
| 输入 | `image` 图像 | `Image(Any)`（必填） |
| 输出 | `image` | **动态**：见下 |

| 压缩方式 | 有损方式 | 输出端口 |
| --- | --- | --- |
| 无损 | — | `Image(Png)` |
| 有损 | JPEG 图像 | `Image(Jpeg)` |
| 有损 | PNG 调色板 | `Image(Png)` |

## 参数

| 参数 | 控件 | 默认 | 何时显示 |
| --- | --- | --- | --- |
| 压缩方式 | 下拉 | 无损 | 总是 |
| 优化力度 | 下拉 | 均衡 | 压缩方式 = 无损 |
| 元数据 | 下拉 | 保留颜色信息 | 压缩方式 = 无损 |
| 有损方式 | 下拉 | JPEG 图像 | 压缩方式 = 有损 |
| 允许的损耗率 | 滑杆 0–100 % | 15 | 有损 **且** 有损方式 = JPEG |
| 颜色数上限 | 滑杆 2–256 | 64 | 有损 **且** 有损方式 = PNG 调色板 |

### 优化力度

| 档位 | 做什么 |
| --- | --- |
| 快速 | 轻量压缩，走 fdeflate，快得多 |
| 均衡 | 日常用这个 |
| 最大 | 逐行滤波的几种策略都编一遍比大小，慢但更小 |
| Zopfli | 在「最大」的基础上，再把压缩数据交给 zopfli 重压一遍 |

越大越慢越小，**任何一档都不会动像素**。

### 元数据

| 档位 | 保留什么 |
| --- | --- |
| 保留颜色信息 | `iCCP` / `sRGB` / `gAMA` / `cHRM` —— 它们决定颜色怎么显示，不当垃圾删 |
| 全部剥离 | 什么都不留，给游戏素材用 |

## 行为约定

- 无损模式不改任何像素：没有透明就不用 RGBA，是灰度就存灰度，颜色少到装得进调色板
  就转索引色，再配上合适的位深。
- **调色板转换是逐像素精确的**：颜色对不上就不会用它。每一步最后都会解回 RGBA 和原图
  逐像素比对，对不上就整个放弃 —— 宁可不优化，也不能悄悄改了图。
- 压完反而变大就原样返回原图，并说明「优化后反而更大」。
- 输入不是 PNG 时（比如 JPEG 选无损）没有可比的对象，会直接算出一份最优 PNG。
  注意这一步通常**变大** —— 有损的源转成无损容器本来就不可能更小。
- JPEG 存不下透明，转过去时透明会被压到白底上并给出提示。
- 「PNG 调色板」用中位切分量化（含 alpha 一起切）。颜色本来就不多于上限时，
  量化这一步一个像素都不会动。

## 实现

`core/src/nodes/compress.rs` 是外壳，干活的在两个模块：

- `core/src/png_opt/` —— 无损优化管线，见[无损 PNG 优化](../png-optimization.md)；
- `core/src/png_quant.rs` —— 中位切分量化。量化完那张图会**再交给** `png_opt`
  去编码，因为颜色一少，索引色编码自己就会被选中。

结果（原大小 → 新大小、节省比例、选中的方案）会写进节点的提示里，在底部运行记录里看得到。

测试：`engine::tests::compress_lossless_keeps_every_pixel`、
`compress_output_type_follows_the_mode`、`lossless_mode_picks_an_indexed_encoding_for_pixel_art`、
`lossy_palette_mode_quantizes_to_an_indexed_png`；`png_opt` 与 `png_quant` 各自还有一整组。
